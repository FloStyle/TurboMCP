> Finding withdrawn — the parameter is documented where a caller looks
>     The first version of this card said `TokenBudget` is documented eight times in the header and zero times in the only published document. Checking the published specification settles it: `Spec/03_TOOLS.md:29` ("large outputs take `TokenBudget` (0 means no limit)"), `:163`, `:205` ("token budget: when the output would pass the budget, step down the detail"), and `Spec/04_FORMATS.md:190-192` ("### Budget steps"). So the parameter is documented in the tool reference and in the format specification, and `TOOLS.md`'s silence is correct and deliberate: measured, every one of its rows is a name index — a tool, one sentence, a source line — and not a reference.
>     How the mistake happened, because the shape recurs: the measurement was sound and the claim built on it was not. One document was measured, then a conclusion was drawn about the documentation as a whole without opening the file whose entire subject is the tools.
>
> Finding confirmed
>     The header claims "it is an estimate, and every tool description that mentions tokens says so". Measured: no tool description in `TurboMCPToolsets.h` contains the word "estimate" or the word "token" as prose. The header uses `TokenBudget` as a parameter name and explains the cap, which is a different statement from calling the figure an estimate, and `TOOLS.md` contains neither word. The claim is a universal — "every ... says so" — and it is false. It is the shape a reader trusts precisely because it is specific. The repair is either to add the word to the descriptions or to delete the sentence; the estimate itself is correct and its own name already says what it is.
>
> What the file gets right
>     The header explains why not "characters divided by four": outputs are S-expressions rather than prose, and most punctuation costs about a token per character, so the naive rule undercounts by half and a budget built on it would let through twice what it promised — a wrong rule, the direction and size of its error, and the consequence of using it. `:22` computes `Total += (RunLength + 3) / 4;` with the identity stated so the expression is not magic. `:15-16` names the double-close before the code performs it, which is the easiest part of this pattern to get wrong. `:37-39` counts whitespace as 0 and every other visible character as 1, naming the four whitespace characters these outputs actually contain. `:46` is the second `CloseRun()` the comment promised.
>
> Tally
>     One finding withdrawn, one confirmed — and the withdrawal is the more useful of the two, because it removes work that would have been done for nothing.

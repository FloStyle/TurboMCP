# Public source preparation

[Release guide](release.md) · [Tracked checklist](../release/public-preparation.json) · [External agent workflow](external-agent-workflow.md)

## Authorization and routes

The owner can authorize an initial **development-source preview** at FloStyle/TurboMCP using reviewed retained history. It exposes source for contribution and testing. Stable 1.0, compatible installation packages, stable release tags and the stable branch require their own [release approval](release-manager.md). Keep the stable release readiness and export approval fields unchanged until that process passes. A successful exporter `--preview` is evidence for a review and grants no publication authority.

The retained-history option applies only to a clean, independent hosting repository. The original private repository and its unsanitized history stay private. It becomes a read-only archive and recovery source after cutover. Keep audit evidence, Git rewrite maps, credentials, engine source and local recovery material outside the published repository. This option supersedes the fresh-root-only publication rule in earlier design and audit records when the owner approves the exact cutover. Their source and verification requirements still apply. A different destination, changed branch set or new source revision requires updated review and authorization. The fresh-root procedure remains available under the existing release gates.

## Verify the complete source tree

1. Select a clean committed source revision and record its full commit and tree IDs. Use a new private scratch location for each candidate and keep prior reviewed evidence.
2. Run `python Tools/export-public.py --preview --output '<new-candidate-directory>'` from the clean committed candidate checkout. Preview reads a staged tree and refuses unstaged tracked edits or unsafe content. Verify that its separate manifest describes the exact candidate commit and tree. Check the full path set, Git file modes, sizes and SHA-256 hashes. Inspect ignored and untracked material for local dependencies separately. The exporter copies every tracked blob and leaves Git ancestry out of the export.
3. Review all current tracked text, field reports, provenance notices, images and native fixtures. Review actual findings and limitations of secret and private-data scans. The icon owner statement and the notice for original replacement tool guidance apply to those current files. Review third-party and fixture provenance separately. Run the scoped native read-only fixture review on the exact fixture bytes. Resolve material content gaps before publication without marking untested behavior as accepted.
4. Run the offline gate in a clean checkout of the final candidate. Confirm it functions independently of private caches, reports, paths and credentials. Keep failed attempts and scope limits in private evidence.

## Review retained history and destination

1. Bind the review to the original source commit, exact input refs, candidate refs and exact destination. Compare hosted branches, tags and relevant pull refs with the intended ref list. Name reviewed aliases and omitted refs in the private evidence. Do not copy the original worktree, remote configuration, hooks, reflogs or alternate object store.
2. Sanitize in a disposable, no-remote mirror. Record the exact filters and original-to-candidate commit map. Confirm the result preserves legitimate ancestry, attribution, dates and notices. Review owner-approved removals and metadata changes. Require Git integrity and reachability checks, no alternate object store and an exact ref inventory. Compare paths, modes and bytes against the input and explain every approved difference.
3. Scan all retained history and the current trees for secret shapes, personal details, private paths, unwanted artifacts and provenance issues. Review findings in commit messages, attribution, paths, text and historical binaries. Resolve actual findings and document residual limits. A scan pass alone establishes neither authorship nor redistribution rights.
4. Record the completed gates and the owner's explicit development-source publication authorization in private evidence. It must identify the reviewed main commit and tree, every additional ref and commit, the destination, the intended visibility and the agreed archive disposition. The same authorization can cover staging, the visibility change after destination checks, and the archive action. After staging, verify the destination heads, tags and other hosted refs, PRs, Actions runs, logs and artifacts. Reject old source objects and private metadata. Stage from the reviewed sanitized mirror using only the authorized refs. Keep the old host and all unsanitized refs private.
5. Verify available controls on the actual destination using the [GitHub checklist](governance.md#github-controls-and-publication-checklist). Keep writes owner-controlled during cutover. Where a control becomes available with public visibility, verify it immediately after the visibility change and before inviting contributions. Verify the public refs and default branch again, then switch development to the new repository and make the private archive read-only. Pause on unexpected refs, metadata, changed identities or unverified destination controls.

The owner may separately authorize a source-only development prerelease tag and GitHub Release page once the approved source and destination checks pass. Bind the tag to the exact reviewed public commit, mark the release as a prerelease, identify the pinned development baseline, and publish the current coverage gaps. A tag such as v1.0.0-dev.20261116 illustrates the format. Source downloads are for development. Leave stable, v1.0.0, installation binaries and release acceptance to the stable release process.

## Fresh-root alternative

If the owner selects a fresh-root publication, initialize a new repository in a disposable copy of the reviewed complete export. Avoid repository templates and shared object stores. Stage every exported file, including ignored tracked paths from the manifest. Restore any 100755 modes from the manifest when preparing the index on Windows. Check that `git write-tree` exactly matches the recorded source tree. Review the author identity and commit message. Verify that the root has no parents, the candidate contains one reachable commit, and no remotes, alternate object store or private refs exist. Apply the same current-tree, destination and owner-authorization gates. The existing stable release evidence remains required for publication through this fallback. Keep the archive and any source-to-public mapping private.

## Stable release

Follow the [release manager checklist](release-manager.md). Use the complete-tree exporter in non-preview mode with the existing release evidence and approval gates. Build and test the exact installation artifact for each claimed engine distribution and record its hash and runtime acceptance. Tag the accepted source and advance stable only under the separate release authorization. An existing approved public history continues through reviewed commits. Preserve and verify the complete source snapshot for each release.
